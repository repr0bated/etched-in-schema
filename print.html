Etched in Schema

Dev cycle: blob → mount → identity

The method is the blob. In 3tched a plugin is its schema, sealed into a blob; a method exists if and only if its blob is in the sealed catalog. The identity (the chatbot / the subsidiary) never calls code directly: it sees the sealed methods as typed files in its own 3tchedFS mount, calls them there, and every call is admitted, checked and receipted by the platform. Every new method built for the hackathon follows this path — that is the dev cycle.

The UI is in the same cycle

The UI is derived from the blobs, never written against a separate API:

StepWhat happens
ScreensRendered from a plugin’s sealed schema (schema_renderer.render_schema) — a new method’s blob gives it a form and result view automatically
ComponentsOnly components declared in the catalog sealed in the json_render blob; a generated spec is validated against that catalog before it is shown
ActionsCall the same sealed method for whoever is acting: a human through the door (the one generic PluginService/CallMethod, with their own credential); the identity through its mount’s call file. Same blob, same capability check, same receipt
ResultsEvery action shows its receipt (operation id, outcome, capability) — and a refusal shows the missing capability

So a new method needs no UI code to appear: seal the blob, and the UI can render and call it. Hand-written UI is only for composition and the governance components (receipt, refusal, approval request, redaction notice). No MCP anywhere in the UI path.

Each plugin is a schema feed

A sealed plugin is not only callable — it publishes itself. Subscribers (the UI, the identity) receive one stream per plugin over the bridge’s Subscribe:

FrameCarries
schema frame (SCHEMA_MIGRATION)the plugin’s sealed schema and its schema hash, so a consumer can render forms and validate before calling
state framescommitted values per object path, each with a generation number (older generations are ignored) and the catalog hash
tombstonesdeletions, so a removed object never reappears from an older frame
withheldprivate state the subscriber is not entitled to stays withheld (withheld-or-unavailable)

The UI keeps feed data under /plugins and /pluginFeeds read-only: a UI can never write state into a feed; only a sealed method call changes it.

How state is read

State has one writer: MutationEngine, which commits the result of each admitted call and only then notifies subscribers. Readers never see an uncommitted value.

ReaderHow
Live consumers (UI, identity)the plugin’s schema feed (above) — values derived from committed state, never from a request payload
Point-in-timecommitted state in shared memory, /dev/shm/opdbus/state/<plugin>.json (root-only; e.g. incus, identity_sled, chat_router, cron, json_render)
Through the mountthe plugin’s read operations (operations/<plugin>/<read-method>/call). The mount’s plugins/<id>/value.json files are meant for this but currently return EIO — use read operations

How state is archived

Nothing is overwritten without a record; history is kept in layers:

LayerWhereWhat it holds
Receipts / chainMutationEngine chain events (operation_id, event_id, event_hash, hash-linked)who did what, under which capability, with which outcome
Snowball/var/lib/opdbus/snowball/{timing,vectors,state,snapshots} — Btrfs subvolumesa streaming audit trail of plugin footprints, automatic read-only snapshots with rolling retention, replicable with btrfs send/receive
VectorsQdrant snowball_footprints (~10k entries)the archived footprints embedded for semantic search (“what changed in X last week?”)
Sealed catalog/var/lib/opdbus/plugin-blobs (persisted copy of the live catalog)which methods existed, by blob hash

For the hackathon this is what makes “every action is attributable” checkable: a receipt in the UI points at a chain event, the snowball keeps the state it produced, and the Web3 index can anchor the chain head.

Steps for a new method (e.g. approvals.request_approval)

  1. Logic, in this repo. Types, rules and tests in a crate here (e.g. approvals/). No I/O. This is the judged, new work.
  2. Register as a plugin, on the platform. A thin schema + dispatch module in /srv/git/odbus-verified/crates/op-plugins/src/state_plugins/<name>.rs, registered in default_registry.rs, calling this repo’s crate. Follow that repo’s AGENTS.md (plugin is the schema; no parallel schema files). Keep it an adapter: decisions stay in this repo’s crate.
  3. Seal a development catalog, without touching live. Build, then opblob seal-plugins <dev-catalog-dir> and inspect the new blob (opblob inspect). The live catalog is unchanged.
  4. Release. The only deploy path is the platform release (./activate-golden.sh → slot activation). After it, the blob is in the live catalog and the operation file appears in the subsidiary’s mount automatically.
  5. Grant. The identity gets the method’s exact capability (an owner-approved grant change). Without it, the call is refused with the capability named — which is itself demonstrable.
  6. Call and verify. As the identity: write arguments to the call file, read the result from the same handle, keep the operation_id and event_hash as evidence.

Etched in Schema

An identity that acts — and can prove what it did.

Etched in Schema is a self-contained 3tched identity — the living embodiment of a business subsidiary — that turns a business goal into deployed, working infrastructure. Every action it takes is authorised against its capabilities, bounded by compliance rules, recorded as a tamper-evident receipt, and anchored on a blockchain so anyone can verify who did what, under what authority, and what actually happened without trusting the agent or its operator.

Built for the Meta Model API hackathon (Startup Track — judged on a working product) by Jeremy Hobson, founder of 3tched.

The method is the blob — the identity acts only through 3tchedFS. Every method is a plugin schema sealed into a blob. The identity’s own 3tchedFS mount projects each sealed method as a typed file (operations/<plugin>/<method>/call); the identity writes arguments there, the bridge admits it by kernel identity, checks the exact capability, commits and returns a receipt. No MCP, no direct API calls, no ovs-* commands. Every new method built here follows: logic in this repo → plugin registration → sealed blob → operation file in the mount → call → receipt. The UI is derived from the same blobs: screens from sealed schemas, actions call the same sealed methods and show their receipts. Each plugin is a schema feed (schema + committed state, streamed); state has one writer (MutationEngine) and is archived as receipts, Btrfs snowball snapshots and vectors. See docs/DEV-CYCLE.md.

Why

AI agents can reason about goals, but they rarely have a durable identity, verifiable permissions, accountable execution, or the ability to build and operate real systems. On-chain artifacts have the mirror-image problem: a contract address or a content hash proves something exists, not that it came from an accountable actor following permitted steps. That missing link between artifacts and accountable, authorised actors is what keeps businesses from trusting both autonomous agents and Web3.

Etched in Schema closes that gap from both sides: every on-chain artifact points to the identity and authorised operation behind it, and every operation points to the artifacts it produced, with the history anchored on-chain.

Goals — the new, judged product

The identity platform (3tched) existed before the hackathon and is used only through its interfaces. The new development, built and judged here, is:

  1. Compliance routing — a business’s requirements become an OSCAL profile; OSCAL tags route each request and each requirement to the components and plugin operations that implement it.
  2. Rule enforcement — boundary rules compile into the capability grants, budgets and network policy that are enforced on every call, with a clear refusal (and the exact missing capability) when a request is out of bounds.
  3. Policy — authoring, versioning and evaluating the rules: what each identity may do, which actions need human approval (two approvals for root), and what happens to data (e.g. PII redaction, retention).
  4. Drop-in consumer app — the existing UI generator repurposed: one spec renders on the web and in tools people already use, starting with team chat — an open-source Matrix client (Element) first, reaching other chat tools through Matrix bridges — and every action is governed by 1–3. Spec: docs/DROP-IN-SPEC.md. A user asks in team chat; the request is routed, checked against policy, executed through the identity or refused, and the receipt comes back in the thread.

The web UI is optional, only if time allows.

Golden path (a working product, end to end, three times in a row before anything else): a user asks the agent in team chat to do something for a business → compliance routing maps it to the required controls and operations → policy is evaluated → allowed operations run through the identity and return receipts; a disallowed one is refused with the reason → the thread shows the result, the receipts, and any redaction applied.

Out of the critical path: the avatar/embodiment, moving identities between hosts, client acquisition, and on-chain anchoring (kept only if it fits once the golden path works).

The project in one paragraph

A self-contained 3tched identity — the “twin”, the living embodiment of a 3tched subsidiary — turns a business goal into deployed, verified infrastructure. It acts only through its own typed filesystem (3tchedFS), every action is authorised against its capabilities and leaves a tamper-evident receipt, and a Web3 index anchored on-chain lets anyone verify who did what, under what authority, without trusting the agent or operator. That link between on-chain artifacts and accountable, authorised actors is the gap blocking Web3 adoption.

Remote identities: established design (owner, 2026-10-28)

WireGuard is only the establishment step: the peer key proves the identity once, the decoy issues the signed peer proof (OIA1) and the session gets its sealed credential (SID1). After that it is zero trust — every call carries the credential and the door’s interceptor re-verifies it, over any transport (internet, Cloudflare). 3tched-fs Credential mode is the remote form of the lungs. The mechanism exists; it needs testing and refinement, not a rebuild. Do not add a mesh (Netmaker/Cloudflare) as an identity layer.

2.2 Governed actions

Every action, on every target, takes one path:

user action (web click / team chat button / team chat command)
  → consumer adapter (identifies the user; no authority of its own)
  → compliance router: request → OSCAL controls → candidate plugin operations
  → policy engine: allow / refuse (with reason) / needs approval (n of m)
  → enforcement: the operation runs through the identity's 3tchedFS call file;
    the bridge checks the exact capability and commits
  → result + receipt rendered back on the same target
  • The adapter never calls plugins directly and never holds grants.
  • A refusal is a first-class result, rendered with the missing capability and the rule.
  • Approvals are collected on the target (chat buttons) and counted by the policy engine; root actions need two approvals — the owner and the policy co-signer (see docs/APPROVALS-SPEC.md).
  • Redaction is applied by policy before content reaches any target; the receipt records it.

2.3 New catalog components

receipt, refusal, approval_request, redaction_notice, policy_decision. They are declared in the catalog like every other component (web and team chat renderers both implement them).

2.4 Generation stays the same

The model (Meta’s) still writes specs from the catalog surface; the spec is validated before rendering on any target. A target-capability filter keeps the model to components the destination supports.

Adapters are thin: parse the event, look up the principal, hand the request to the router, render the reply. All decisions happen in routing, policy and enforcement, so every surface behaves identically.

4. Acceptance criteria (the working product)

  1. A spec that renders on the web renders in team chat with the same actions.
  2. From team chat, an allowed request runs through the identity and the thread shows the result and its receipt (operation id, outcome).
  3. An out-of-bounds request is refused in team chat with the exact missing capability and the rule.
  4. A root-level request shows an approval request and runs only after both the owner and the policy co-signer approve (see docs/APPROVALS-SPEC.md).
  5. Content with PII posted through the drop-in is redacted before display, with a redaction notice and receipt.
  6. The model (Meta) generates a spec from the catalog; invalid specs are rejected before rendering.

5. Out of scope

New UI frameworks (web stays Svelte + json-render), direct plugin calls from adapters, adapters holding grants, a second policy engine per target.

6. Generated backends (owner direction, 2026-10-28)

The system does not adopt an existing CMS. It references them (Payload, Strapi, Wagtail, Ghost, Decap) as a feature checklist and data-model source — content types and fields, relations, roles, draft/review/publish, versioning, media, webhooks — and generates its own backend:

  • A generated CMS is a 3tched-native definition: content types are schemas, promoted to a sealed plugin; content lives in Cozo through MutationEngine; every create/edit/publish is a receipted mutation; policy, redaction and approvals apply at write time; the UI comes from the existing generator.
  • The model generates definitions, never backend code. From a business declaration and the reference feature set, Meta’s model produces content types, fields, roles, workflows and policies; the definition is validated against a fixed meta-schema (like UI specs against the catalog).
  • Fixed, tested code implements CRUD, publish, versioning, redaction and receipts once, for any valid definition — so no generated backend can carry a bug the model invented.

Approvals spec: two-approval root, policy co-signer, break-glass

How these methods reach the identity: sealed blob → 3tchedFS operation file → call → receipt. See DEV-CYCLE.md.

Part of the judged policy and rule enforcement work. Status: planned (nothing here is built yet). Existing platform pieces are marked existing.

1. Goal

No root-level action runs on one say-so. Routine root actions need the owner and a policy co-signer (the control-plane chatbot); anything outside written policy is refused unless the owner uses an audited break-glass path. Every decision — approve, refuse, override — produces a receipt with reasons.

2. Actors

ActorIdentityRole
Ownerhuman principal <owner-principal>, session <owner-session> (existing, containerless)requests and approves root actions
Co-signercontrol-plane chatbot (root identity; today <subsidiary-principal>)approves by policy only; never executes
Executorthe identity that performs the operation (e.g. the Hackathon subsidiary)runs the operation after approval, through its mount
Latera designated human second approverreplaces the co-signer for the highest tier

The root identity holds authority but never executes (owner rule).

3. Tiers

TierWhenNeeds
Routine rootoperation is root-level and within written policyowner approval + co-signer approval
Out of policyco-signer finds a policy condition unmetrefused; only break-glass can proceed
Break-glassowner overrides a refusalfresh hardware-key confirmation + cancellable delay + receipt anchored on-chain + second-channel notice

Non-root operations keep today’s behaviour: the bridge’s per-call capability check (existing).

4. Data model

ApprovalRequest {
  id: uuid                      # request id
  operation: { plugin, method } # e.g. ovsdb_bridge.create_bridge
  arguments_hash: sha256        # of canonical JSON arguments; arguments stored, not free text
  resource: string              # e.g. "bridge:etched0"
  executor: session_id          # identity that will run it
  requested_by: principal_id    # owner
  policy_ref: { profile, control_ids[], version }
  created_at, expires_at        # short TTL (e.g. 10 min)
}

Approval {
  request_id, approver_principal, kind: owner|cosigner|human,
  decision: approve|refuse, reasons[], judgments{}?, receipt: operation_id/event_hash
}

BreakGlass {
  request_id, hardware_key_assertion, delay_s, cancelled: bool,
  anchor: { chain_id, tx | attestation_uid }, notice_channel
}

The request is structured: the co-signer never sees free-text justification from the requester.

5. Co-signer decision (judgments from the model, decision in code)

The co-signer answers atomic questions about the structured request (the chatbot via Meta’s model, or Jev nouls); code decides from fixed thresholds (yes ≥ 0.7, no ≤ 0.3, otherwise unsettled).

Judgment (noul)Meaning
in_declared_boundaryIs resource inside the executor’s declared boundary in policy_ref?
operation_permitted_by_controlDoes a control in policy_ref permit this operation on this resource?
executor_matches_requestIs the executor the identity the policy assigns to this kind of operation?
destructiveWould this operation delete or overwrite existing state?
affects_shared_infrastructureDoes it touch infrastructure other identities depend on (e.g. ovsbr0)?

Truth table (in code):

in_boundarypermittedexecutor_okshared_infradestructiveDecision
yesyesyesnoanyapprove
yesyesyesyesanyrefuse (break-glass only)
no or unsettled————refuse
—no or unsettled———refuse
——no or unsettled——refuse

destructive does not change the decision; it is recorded and raises the break-glass delay. Exact-match facts (does resource equal an allow-listed value, is the request expired) are checked in code, not asked of the model.

6. Flow

owner request (UI / team chat / mount)
  → build ApprovalRequest (structured; arguments hashed and stored)
  → owner approval (signed by owner session)
  → co-signer: judgments → code decision → Approval + receipt
      approve → issue a single-use execution ticket (existing elevation.authorize_task style, 60 s)
      refuse  → show the reasons; offer break-glass
  → executor runs the operation through its 3tchedFS call file with the ticket;
    the bridge checks the exact capability (existing) → operation receipt
  → result + all receipts shown to the owner

Break-glass: owner chooses override → hardware-key assertion (e.g. FIDO2/WebAuthn) → delay (cancellable from any owner device) → notice on a second channel → anchor the BreakGlass record on-chain → issue the ticket → execute as above.

7. Enforcement points

  • A root-tier operation without a valid ticket (two approvals or break-glass) is refused before execution, with the reason.
  • Tickets are single-use, bound to request_id, arguments_hash, executor and a short TTL; a mismatch is refused.
  • The co-signer cannot approve its own requests and holds no execution grants.
  • All receipts are append-only; refusals are receipted too.

8. Acceptance criteria

  1. A routine root action within policy runs only after owner + co-signer approval; both approvals and the operation have receipts.
  2. A request on a resource outside the boundary (e.g. bridge:ovsbr0) is refused by the co-signer with the failed judgment named.
  3. Free-text added to a request does not change the co-signer’s decision (test: same structured request ± persuasive text → same decision).
  4. Break-glass requires the hardware-key step and the delay, can be cancelled during the delay, and leaves an anchored record.
  5. Reusing a ticket, changing arguments after approval, or executing after expiry is refused.

Subsidiaries and the identity sled

How an identity works as the embodiment of a subsidiary. Marked existing (in 3tched today), proven (demonstrated 2026-10-28) or planned.

Hierarchy (owner model)

  • Root: the 3tched control plane — the only root on the system. Its chatbot is a one-off part of the system core, to be fused with the WireGuard server key so it can never be a peer (session <root-session>). Planned — no supported re-key operation yet.
  • Root has no execution rights: it holds authority but executes nothing itself; execution is delegated through the execution tracker. A human acting as root needs two approvals (two-person rule). Today elevation offers a single-use ticket (authorize_task, 60 s TTL); the second approval is new work. Planned.
  • Owner override (owner requirement): while the owner is the only human, his identity must be able to override the two-approval rule. Proposed: routine root actions take two approvals from two independent owner devices (session + hardware key/phone); an override is break-glass — fresh hardware-key confirmation, a cancellable delay, a receipt anchored on-chain, and a notification on a second channel — so even the owner cannot act as root silently. A designated human second approver replaces this later. Planned.
  • Second approver = the control-plane chatbot (owner decision): it co-signs the owner’s root actions by policy, not persuasion — it receives only a structured request (operation, resource, identity, applicable policy), never free-text justification; atomic judgments (the chatbot or Jev) feed code that decides approve/refuse; anything outside written policy is refused and only break-glass can override; every decision is receipted with its reasons. It approves but never executes. Tiers: routine = owner + chatbot within policy; out of policy = refused, break-glass only; later = human second approver. Planned.
  • Subsidiaries: Linux users on the system. Each subsidiary is bounded by its home directory. Planned.
  • Hackathon subsidiary: embodied by identity <subsidiary-session> (today’s 3tchedCtlChatbot). Existing.

Prior art and positioning

How Etched in Schema relates to production identity systems, and what it adds. Use this for the pitch, the YC application, and design decisions.

The pattern is proven in production

The remote-identity design (establish once, then zero trust over any transport) matches SPIFFE/SPIRE, the CNCF standard for workload identity:

3tchedSPIFFE/SPIRE equivalent
Kernel-peer check on the lungs Unix socketSPIRE Unix workload attestor — identifies the calling process over a Unix socket using kernel peer credentials (same mechanism)
WireGuard key establishes the identity once (decoy issues OIA1, session gets SID1)Node attestation: the machine proves itself once (cloud identity document, TPM, join token)
Sealed credential (SID1), then zero trust over any transportShort-lived SVIDs (X.509/JWT) verified on every connection (mutual TLS)
Door interceptor re-verifies every callEach service verifies the peer’s SVID per request

Other production relatives:

  • Google BeyondCorp, Cloudflare Access — zero trust: nothing is trusted for being on the network; every request is verified against identity and policy.
  • AWS IAM Roles Anywhere, cloud instance identity — a workload proves itself once, then uses short-lived credentials from anywhere.
  • W3C DIDs and Verifiable Credentials — the standard for portable, self-controlled identity anyone can verify; the Web3-adjacent reference.

What 3tched adds (the differentiators)

  1. The identity is the entity, not a label. SPIFFE names a workload whose state and history live elsewhere. In 3tched the identity is the key, genesis and receipt chain, with its own container, memory and storage.
  2. Capability per typed operation. SPIFFE answers “who is this?” and leaves “what may it do?” to each service. 3tched checks the exact capability for each schema-declared operation centrally and records a receipt.
  3. Verifiable history. Workload identity proves who is calling now. 3tched adds a tamper-evident record of everything the identity has done, anchorable on-chain.
  4. Compliance by construction. OSCAL requirements compile into the grants, budgets and network policy that are actually enforced, with receipts as the assessment evidence.

Transport and identity (decided)

  • WireGuard is only the establishment step; after that the credential carries identity over any transport. The mechanism exists; it needs testing and refinement.
  • Netmaker (WireGuard mesh) would only add connectivity; it is retired from 3tched and not needed.
  • Cloudflare (WARP/mesh) is acceptable as a pipe, never as the identity layer: devices authenticate to Cloudflare with Cloudflare’s keys, so the bridge would see a Cloudflare address, not the identity’s key. Identity stays proven end to end by the credential.
  • Sealed blobs (schemas) are content-addressed: they travel with the identity or are fetched by hash over any channel and verified.
  • What the model depends on: credential binding to the key, expiry, revocation, and replay refusal. Known gap (HANDOFF, 2026-09-25): the interceptor still mints genesis server-side when no session exists, and the decoy mints only OIA1 — verify before relying on remote identities.

Pitch lines

  • “Workload identity like SPIFFE proves who is calling. Etched in Schema also proves what the identity was allowed to do — and what it actually did.”
  • “Every on-chain thing the agent creates comes with a verifiable answer to who did it, what they were allowed to do, and what really happened.”
  • “Implements and evidences these controls” — never “compliant” or “certified”.

How to win this hackathon

Ten priorities for the demo and submission. When in doubt, choose whatever makes the golden path more reliable or more verifiable.

  1. Unforgettable first 30 seconds. The avatar speaks the exact intro script, then immediately does one real thing, with its receipt appearing on screen. Show proof before explaining anything.

  2. Let a judge verify something themselves. Hand them a receipt ID or on-chain anchor and a one-step way to check it (link or QR code). “Don’t trust me, check it” is the thesis made physical.

  3. Show one refusal live. Ask the identity to do something outside its OSCAL boundary; the bridge refuses with the exact missing capability. An agent that can’t misbehave beats one that doesn’t.

  4. Use Meta’s model visibly and well. Show Muse Spark doing the reasoning (planning the business, mapping requirements to controls), say so on screen, and let it make one real tool call through the identity’s mount.

  5. Protect the golden path above everything. Intro → “create a CMS for this business” → provision → receipts → anchor. Run it end to end daily from Day 5. If it does not pass three times in a row, add nothing new.

  6. Redaction is the “wow” moment. Content with a name, email and phone number is published and masked automatically, with the receipt naming the policy. Everyone understands it instantly.

  7. A fallback for every live dependency. Record a full run and know the exact step at which you would switch to it. Model, chain or Wi-Fi can fail on stage; a calm switch still scores.

  8. Tell a story with a real business. One believable small business (e.g. a Fort Lauderdale firm that needs a compliant client portal), with a name and a problem, solved by the identity.

  9. Say the positioning line out loud. “Workload identity like SPIFFE proves who is calling. Etched in Schema also proves what it was allowed to do — and what it actually did.”

  10. Ship the evidence, not just the demo. Public repo with a README that separates new from pre-existing work, a short video, a one-page architecture diagram, and a live link judges can open later.
